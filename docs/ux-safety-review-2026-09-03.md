# P2P Check UX·안전성 검토 — 2026-09-03

## 목적

돈을 다루는 P2P 계산·공유 도구의 안전장치는 보수적으로 유지하되, 사용자가 매 화면에서 경고문을 읽어야만 안전해지는 구조는 피한다. 안전은 가능한 한 입력 검증, 서버 검증, 만료·stale 차단, 서명·lifecycle과 같은 동작으로 강제하고, 화면에는 현재 행동에 필요한 설명만 노출한다.

## 기준 상태

- production 기준: `main` v2.2.3
- 안전성 강화 후보: `staging` v2.3.0
- 이번 작업 브랜치: `review/ux-safety-20260903`
- 검토 시점 원격 브랜치: 29개
- `main`은 변경·병합·배포하지 않는다.

`staging`은 `main`과 단순 선후 관계가 아니다. 검토 시점에 `staging`은 공통 기준점 이후 20개 커밋이 앞서지만, `main`의 최근 3개 커밋은 포함하지 않은 diverged 상태다. 따라서 어느 한 브랜치를 다른 브랜치에 그대로 덮어쓰는 방식은 사용하지 않는다.

- `optimize/final-main-cleanup-v2`

`backup/*`, 과거 `feature/receive-info-*`, `codex/p2p-v2-selective-review`, 과거 maintenance/experiment 브랜치는 아이디어와 이력 보존에는 가치가 있지만 현재 기준선으로 다시 병합해서는 안 된다. 필요한 아이디어만 현재 코드에 재검증 후 선택적으로 옮기는 방식이 안전하다.

## 확인한 좋은 안전 설계

특히 `staging`에는 다음 항목이 이미 강하게 구현되어 있으므로 UX 정리 과정에서 약화시키지 않는다.

- BOLT11 금액·서명·만료 검증과 120초 경계 lifecycle
- 만료된 인보이스 QR·복사 즉시 중지
- 거래 조건 변경 시 기존 결제정보 stale 처리
- 업비트 기준가 서버 재검증과 stale 공유 차단
- Lightning Address/LNURL 외부 요청의 deadline·redirect·응답 크기 제한
- 거래기록 pending/finalize/revoke lifecycle과 철회 capability
- 기록 서명과 신원·입금·수령 증명의 의미 분리
- 320px 화면, 44×44 조작 대상, 접근성 자동검사
- CSP, API 보안 헤더, 비프로덕션 격리와 fail-closed 배포 정책
- 앱·Worker typecheck, Node/Worker/Playwright/axe/PWA를 포함한 검증 게이트

거래 모집글도 공개 채널에 결제 주소·인보이스·구체적인 자금 출처 값을 자동으로 싣지 않고, 전송 방식과 신원·자금 출처 설명 가능 여부는 선택 항목으로 둔다. 기본 전송 방식이 온체인인 점도 사용자가 실제로 지원하지 않는 라이트닝 거래를 실수로 모집하지 않게 하는 보수적인 기본값으로 판단했다.

## 사용자 관점에서 확인한 문제와 조치

### 1. 안전한 행동이 첫 번째 행동으로 보이지 않음

온체인 수취정보에서 `주소만 포함`이 `금액 포함 QR 만들기`보다 먼저 배치되어 있었다. 라이트닝도 `주소만 포함`과 결제용 인보이스 생성이 한 수준에 노출된다.

돈을 보내는 도구에서는 금액이 결제 요청에 결합되는 경로를 기본 행동으로 두고, 주소만 전달하는 경로는 보조 행동으로 두는 편이 오류 가능성을 줄인다.

조치: 온체인은 `금액 포함 QR 만들기`, 라이트닝은 `결제용 인보이스 만들기`를 primary이자 첫 번째 행동으로 배치한다.

### 2. 구현 용어가 기본 사용자 흐름에 과다 노출됨

기본 화면에서 BIP21, LNURL-pay, BOLT11, 메인넷·서명 등 구현 용어가 연속으로 노출된다. 검증 자체에는 필요하지만 사용자가 결제정보를 만들기 위해 프로토콜 명칭을 이해할 필요는 없다.

조치: 기본 경로는 `온체인 주소`, `라이트닝 주소`, `결제용 인보이스` 중심으로 표현한다. 직접 인보이스 입력과 오류 메시지처럼 기술적 구분이 실제 판단에 필요한 곳에는 정확한 용어를 유지한다.

### 3. `초기화`가 실제 결과를 설명하지 못함

유효한 결제정보가 있으면 거래 금액과 시세 기준을 고정한다. 시간이 지나 시세가 stale해지면 사용자는 결제정보를 해제해야 새 시세로 다시 계산할 수 있는데, 버튼이 단순히 `초기화`로 되어 있어 복구 경로가 직관적이지 않았다.

조치: `결제정보 지우기`로 이름을 바꾸고, 결과 영역에서 `새 시세로 다시 계산하려면 결제정보를 지우십시오`라고 행동을 직접 안내한다.

### 4. 공유 전 상태가 이미 공유된 것처럼 보임

결제정보를 준비한 직후 상태가 `카드에 포함됨`으로 표시된다. 이 시점에는 거래기록 카드가 아직 생성·공유되지 않았을 수 있다.

조치: 상태를 `사용 가능`으로 바꾼다. expiring/expired/stale도 `사용 중지`로 표현해 실제 lifecycle과 맞춘다.

### 5. 보안 문구의 반복이 핵심을 약하게 만듦

계산기 하단에는 항상 거래 확인 문구가 있고, 검증 화면에도 긴 disclaimer가 있다. 사용자는 반복되는 문장을 배경 정보로 무시하기 쉽다.

조치: 계산기 전역 footer 경고는 제거한다. 검증 화면에서는 거래 조건을 결제정보보다 먼저 보여주고, 결제 직전에 `서명은 기록 무결성만 확인하며 신원·입금·수령은 별도 확인해야 한다`는 범위만 짧게 남긴다.

## 추가 재검토 결과

### 역할 전환 시 금액 유지

초기 구조만 보면 buyer/seller별 금액 상태가 분리되어 있어 역할 전환 시 과거 숨은 값이 나타날 가능성을 의심할 수 있다. 실제 `changeTradeRole` 구현을 다시 추적한 결과, 역할을 바꿀 때 현재 계산된 원화 또는 BTC 금액과 현재 입력 기준을 새 역할 상태로 복사한 뒤 역할을 전환한다.

따라서 현재 `staging`에서는 `삽니다 ↔ 팝니다` 전환 때문에 과거 금액이 갑자기 복원되는 문제를 결함으로 판정하지 않는다. 이 동작이 향후 리팩터링에서 사라지지 않도록 UX 안전 계약 테스트에 포함한다.

### `main` 시세 정책의 선택적 계승

`main` v2.2.1~v2.2.3의 최근 변경을 커밋 단위로 합치지 않고 기능별로 재검토했다. 다음 항목은 현재 hardening 구조와 충돌하지 않으므로 이번 후보에 선택적으로 이식한다.

- WebSocket이 정상일 때 업비트 프리미엄·mempool 참고값 REST 갱신을 5분 주기로 제한
- WebSocket이 끊겼을 때 가격 포함 REST fallback을 60초 주기로 사용
- WebSocket 재연결을 15초 → 30초 → 60초로 백오프하고 이후 60초 유지
- 정상 실시간 체결가를 받으면 재연결 단계를 초기화
- 화면 복귀 또는 온라인 복귀 시 REST 확인을 즉시 1회 수행
- 프리미엄과 수수료 카드에 마지막 갱신 시각을 표시
- 프리미엄 카드의 중복 `업비트 데이터랩 · 시장 참고값` 문구 제거

반대로 `staging`의 `LIVE_STREAM_STALL_TIMEOUT_MS` 기반 watchdog은 제거하지 않는다. 실시간 메시지가 멈추면 약 20초 경계에서 즉시 stale로 바꾸고 공유를 차단한 뒤 REST 확인을 수행한다. 따라서 정상 상태의 불필요한 REST 호출은 줄이면서, 실시간 스트림 장애 감지는 기존 hardening 수준을 유지한다.

이 결합은 `main` 파일을 덮어쓰는 방식이 아니라 `market-refresh` 정책과 현재 WebSocket lifecycle을 직접 통합한 것이다. 회귀시험은 5분/60초 주기, 15·30·60초 백오프와 기존 watchdog이 동시에 존재해야 통과하도록 수정한다.

## 이번 브랜치에서 의도적으로 건드리지 않은 문제

### A. `P2PTradeTool.tsx`의 책임 과밀

시세 연결, 계산 상태, 초안 저장, 공유 준비, 거래기록 lifecycle, 철회 복구, 결제정보 lock이 한 컴포넌트에 집중되어 있다. 현재는 테스트가 강해 기능적으로 방어하고 있지만 작은 UX 수정도 넓은 회귀 범위를 만든다.

향후 `market session`, `trade draft`, `share session`, `payment lock`을 상태 훅 또는 순수 상태 머신으로 분리하는 것이 유지보수 안전성에 유리하다. 단, 구조 리팩터링과 UX 변경을 한 릴리스에 섞지 않는다.

### B. production 승격 정책

`staging` 감사 문서가 명시하듯 v2.3 production 배포는 Durable Object compatibility 전환, Cloudflare/GitHub 외부 설정, 키 관리·복구·실기기 검증 등이 완료되기 전 fail closed 상태다. 이번 UX 브랜치는 이 배포 차단을 해제하지 않는다.

## 적용 원칙

1. 안전은 경고문보다 코드로 강제한다.
2. 기본 버튼은 가장 오류 가능성이 낮은 행동으로 둔다.
3. 사용자가 복구해야 하는 상태에는 원인이 아니라 다음 행동을 명확히 쓴다.
4. 서명·검증의 의미를 과장하지 않는다.
5. 고급 프로토콜 용어는 실제 판단에 필요할 때만 노출한다.
6. production과 `main`은 별도 승인 전 변경하지 않는다.
